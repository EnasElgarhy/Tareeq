Extensible Schema Design Guide
For Developer: Ahmed Wahba

Overview
“Extensible” means the database can grow and change without breaking existing code or requiring complex migrations.
Goal: Build MVP fast, but design it so Phase 2 and Phase 3 additions don’t require rewriting everything.

Core Principle: Add, Don’t Change
✅ Good (Extensible)
-- Phase 1: Create table with basic fields
CREATE TABLE assessment_data (
  assessment_id UUID PRIMARY KEY,
  final_cluster VARCHAR(50),
  created_at TIMESTAMP
);

-- Phase 2: Add new column (doesn't break existing code)
ALTER TABLE assessment_data 
ADD COLUMN riasec_scores JSON;
❌ Bad (Not Extensible)
-- Phase 1: Create table
CREATE TABLE assessment_data (
  assessment_id UUID PRIMARY KEY,
  final_cluster VARCHAR(50)
);

-- Phase 2: Rename column (breaks existing code!)
ALTER TABLE assessment_data 
RENAME COLUMN final_cluster TO primary_career_cluster;
Rule: Never rename or delete columns. Always add new ones.

Strategy 1: JSON Columns for Future Flexibility
Use JSON for data structures that might change or expand.
Example: Question Responses
Problem: Questions might change. Q1-Q40 in Phase 1, but what if Phase 2 adds Q41-Q50?
Solution: Store responses as JSON, not fixed columns.
-- ✅ Good: Flexible
CREATE TABLE assessment_data (
  responses JSON -- {"q1": "A", "q2": "C", "q3": "B"}
);

-- Can later handle Q41-Q50 without schema change
-- Just store: {"q1": "A", ..., "q41": "D", "q42": "A"}
-- ❌ Bad: Rigid
CREATE TABLE assessment_data (
  q1_response VARCHAR(1),
  q2_response VARCHAR(1),
  -- ... 40 columns
);

-- Adding Q41 requires ALTER TABLE (painful)
When to use JSON: - Question responses (might add questions) - Cluster rankings (might add clusters) - RIASEC scores (Phase 2 addition) - Functional cluster data (Phase 3 addition) - Any array or nested object

Example: Cluster Rankings
Phase 1: 8 career clusters
Phase 3: Might add 2 more clusters (e.g., “Healthcare”, “Education”)
Extensible design:
-- ✅ Good
cluster_rankings JSON
-- [
--   {"cluster": "Technology", "score": 6.5},
--   {"cluster": "Engineering", "score": 5.0},
--   ...
-- ]

-- Phase 3: Just add more objects to JSON array
-- No schema change needed
-- ❌ Bad
technology_score DECIMAL(5,2),
engineering_score DECIMAL(5,2),
science_score DECIMAL(5,2),
-- ... 8 fixed columns

-- Adding new cluster = ALTER TABLE (breaks things)

Strategy 2: Placeholder Columns for Known Future Additions
If you KNOW you’ll add something in Phase 2/3, add the column now but leave it NULL.
Example: RIASEC Scores (Phase 2)
CREATE TABLE assessment_data (
  assessment_id UUID PRIMARY KEY,

  -- Phase 1 data (populated now)
  final_cluster VARCHAR(50) NOT NULL,
  confidence_percentage INTEGER NOT NULL,

  -- Phase 2 placeholders (NULL for now, populated later)
  riasec_scores JSON DEFAULT NULL,
  riasec_code VARCHAR(10) DEFAULT NULL,

  -- Phase 3 placeholders (NULL for now)
  functional_cluster VARCHAR(50) DEFAULT NULL,
  onet_soc_codes JSON DEFAULT NULL
);
Why this works:
No cost: NULL columns use minimal storage
No breaking changes: Existing code ignores NULL columns
Easy to populate later: Just UPDATE where NULL
Phase 2 code can do:
// Calculate RIASEC from existing CORE data
const riasecScores = calculateRIASEC(assessment);

// Update existing records
await db.assessment_data.update(
  {
    riasec_scores: riasecScores,
    riasec_code: getRIASECCode(riasecScores)
  },
  {
    where: { riasec_scores: null } // Only update records without RIASEC
  }
);
No ALTER TABLE needed. No downtime. No migration risk.

Strategy 3: Metadata Fields for Version Tracking
Track which version of the assessment generated each result.
CREATE TABLE assessment_data (
  assessment_id UUID PRIMARY KEY,

  -- Version tracking
  assessment_version VARCHAR(10) NOT NULL, -- 'v1.0', 'v1.1', 'v2.0'
  questions_version VARCHAR(10) NOT NULL, -- 'q1.0', 'q1.1'
  scoring_algorithm_version VARCHAR(10) NOT NULL, -- 's1.0', 's1.1'

  created_at TIMESTAMP NOT NULL
);
Why this matters:
If you change questions or scoring in Phase 2, you can: - Compare results from v1.0 vs v2.0 - Offer users “retake with new version” - Run validation studies (does new scoring improve prediction?)
Example use:
// Phase 2: You improved the scoring algorithm

// Recalculate all v1.0 assessments with v2.0 algorithm
const v1Assessments = await db.assessment_data.findAll({
  where: { scoring_algorithm_version: 's1.0' }
});

for (const assessment of v1Assessments) {
  const newScores = scoringAlgorithmV2(assessment.responses);

  // Store both old and new for comparison
  await db.assessment_comparisons.create({
    assessment_id: assessment.assessment_id,
    old_version: 's1.0',
    new_version: 's2.0',
    old_cluster: assessment.final_cluster,
    new_cluster: newScores.final_cluster,
    agreement: assessment.final_cluster === newScores.final_cluster
  });
}

// Research question: "Does v2.0 change predictions significantly?"

Strategy 4: Separate Tables for New Features
Don’t cram everything into one table. Use related tables for Phase 2/3 features.
Example: User Outcomes (Phase 2)
Don’t add to assessment_data:
-- ❌ Bad: Bloats main table
ALTER TABLE assessment_data
ADD COLUMN actual_university VARCHAR(255),
ADD COLUMN actual_major VARCHAR(255),
ADD COLUMN actual_career VARCHAR(255),
ADD COLUMN satisfaction_rating INTEGER;
Create separate table:
-- ✅ Good: Clean separation
CREATE TABLE user_outcomes (
  outcome_id UUID PRIMARY KEY,
  assessment_id UUID REFERENCES assessment_data(assessment_id),

  followup_date TIMESTAMP,
  actual_university VARCHAR(255),
  actual_major VARCHAR(255),
  satisfaction_rating INTEGER,

  created_at TIMESTAMP
);
Benefits:
assessment_data stays fast (no extra columns)
user_outcomes only has data for users who responded to follow-up
Can have multiple follow-ups per assessment (6mo, 12mo, 24mo)

Strategy 5: Foreign Keys for Relationships
Use proper foreign keys so tables can reference each other safely.
-- Parent table
CREATE TABLE assessment_data (
  assessment_id UUID PRIMARY KEY,
  -- ... fields
);

-- Child table with foreign key
CREATE TABLE user_outcomes (
  outcome_id UUID PRIMARY KEY,
  assessment_id UUID REFERENCES assessment_data(assessment_id) ON DELETE CASCADE,
  -- ... fields
);
ON DELETE CASCADE means: If assessment deleted, outcomes deleted too (keeps data clean).

Strategy 6: Avoid Hard-Coding Values
Don’t hard-code lists that might grow.
❌ Bad: Hard-coded in schema
CREATE TABLE assessment_data (
  final_cluster ENUM(
    'Technology',
    'Engineering', 
    'Science',
    'Arts',
    'Business',
    'Law',
    'People',
    'Environment'
  )
);
Problem: Adding 9th cluster requires ALTER TABLE.
✅ Good: VARCHAR with validation in code
CREATE TABLE assessment_data (
  final_cluster VARCHAR(50) NOT NULL
);
// Validation in application code (easy to change)
const VALID_CLUSTERS = [
  'Technology',
  'Engineering',
  'Science',
  'Arts',
  'Business',
  'Law',
  'People',
  'Environment'
];

function validateCluster(cluster) {
  if (!VALID_CLUSTERS.includes(cluster)) {
    throw new Error(`Invalid cluster: ${cluster}`);
  }
}
To add 9th cluster: Just update VALID_CLUSTERS array. No database migration.

Strategy 7: Migration-Friendly Defaults
When adding columns later, use sensible defaults so existing rows don’t break.
-- Phase 2: Adding new column
ALTER TABLE assessment_data
ADD COLUMN riasec_calculated BOOLEAN DEFAULT FALSE;
All existing rows automatically get FALSE. No manual updates needed.
-- ❌ Bad: No default
ALTER TABLE assessment_data
ADD COLUMN riasec_calculated BOOLEAN; -- NULL for existing rows, causes bugs

Common Mistakes to Avoid
Mistake 1: Using SELECT * in code
// ❌ Bad: Breaks when new columns added
const assessments = await db.query('SELECT * FROM assessment_data');
// ✅ Good: Explicitly list columns
const assessments = await db.query(`
  SELECT 
    assessment_id,
    final_cluster,
    confidence_percentage,
    created_at
  FROM assessment_data
`);
Why: Adding new columns to table won’t break code that only selects specific columns.

Mistake 2: Not handling NULL values
// ❌ Bad: Assumes riasec_scores always exists
const riasecCode = assessment.riasec_scores.code; // Crashes if NULL
// ✅ Good: Check for NULL
const riasecCode = assessment.riasec_scores?.code || 'Not calculated yet';

Mistake 3: Changing field types
-- ❌ Bad: Changes data type (breaks code!)
ALTER TABLE assessment_data
ALTER COLUMN confidence_percentage TYPE VARCHAR(10);
-- ✅ Good: Add new column if needed
ALTER TABLE assessment_data
ADD COLUMN confidence_label VARCHAR(20); -- 'high', 'medium', 'low'

Testing Extensibility
Before deploying schema, test that it’s extensible:
// Test 1: Can add new columns without breaking existing queries?
async function testAddColumn() {
  // Add a column
  await db.query('ALTER TABLE assessment_data ADD COLUMN test_column TEXT');

  // Old query should still work
  const result = await db.query('SELECT assessment_id, final_cluster FROM assessment_data LIMIT 1');

  assert(result.length > 0);
  console.log('✅ Adding column doesn\'t break existing queries');
}

// Test 2: Can JSON fields handle new keys?
async function testJSONExtensibility() {
  // Phase 1: Store with 40 questions
  await db.assessment_data.create({
    responses: {q1: 'A', q2: 'B', /* ... */, q40: 'D'}
  });

  // Phase 2: Store with 50 questions
  await db.assessment_data.create({
    responses: {q1: 'A', q2: 'B', /* ... */, q50: 'C'}
  });

  // Both should work
  const all = await db.assessment_data.findAll();
  assert(all.length === 2);
  console.log('✅ JSON fields handle different structures');
}
